# Backend invariants / compatibility

1. **Tenant isolation** is application `organization_id` scoping + API-key/JWT queue ACL. RLS is not a live backstop.
2. **Idempotent enqueue** when `idempotency_key` set: unique per org.
3. **At-least-once** processing: leases + retry + DLQ; workers must be idempotent.
4. **gRPC proto3 zeros** for `max_retries` / `timeout_seconds` mean “server default 3/300”, not zero. Documented in enqueue code comments. The same holds for `lease_duration_secs` / `extension_secs` on `Dequeue`, `StreamJobs`, `ProcessJobs` and `RenewLease`: `<= 0` is `GRPC_DEFAULT_LEASE_DURATION_SECS` (default 300; `0`/blank/unset = 300, above 3600 lowered to 3600, at or below `WORKER_HEARTBEAT_INTERVAL_SECS` or below 5 refused by `Settings::validate`; `config::WorkerSettings::grpc_default_lease_duration_secs`, `grpc/services/queue_service.rs:273` `lease_secs`, `grpc/mod.rs:91`), and `Register` reports that value. It is deliberately **not** the REST `WORKER_LEASE_DURATION_SECS` (30): the Go SDK `StreamJobs` has no lease parameter and the Go/PHP `Dequeue`/`RenewLease` send 0 unless set, so tying omitted gRPC leases to the REST default re-delivers their longer jobs to a second worker (W3R-03, backward compatibility wins). Explicit leases keep the 5..3600 clamp. Never hard-code a gRPC lease constant; change the setting. The default lease must stay above the heartbeat interval: `0` used to become a 5 s lease (and 1-9 a 5-9 s one) under the 10 s heartbeat, re-delivering every job of a worker that sends none.
5. **REST may send `max_retries: 0`** (instant DLQ on first fail). Clients must not assume REST and gRPC omit-semantics are identical for zero.
6. **Stripe webhook** must verify signature; events must be deduped; prefer a non-2xx over silent drop for ordering/link races (409 `CONFLICT` for an event whose customer is not linked yet, 5xx for failures; both are retried by Stripe). **A completed checkout is trusted to name an org only through `metadata.spooled_org_id`**, which only `POST /billing/checkout` sets; `client_reference_id` (public Payment Links) is untrusted, links only an org with no live subscription and a verified billing email equal to the payer's, and never cancels anything (BEBILL-02). A replaced subscription is recorded in `organizations.stripe_superseded_subscription_ids` by the relink itself and removed only after Stripe confirms the cancel; the org's current subscription is never cancelled (BEBILL-14). See `dataflows/billing-stripe.md`.
7. **Plan limits** gate enqueue/resources; changing `config/plans.rs` or env plan overrides is a money-path change — owner sign-off.
8. **OpenAPI** is hand-maintained — update `docs/openapi.yaml` when changing public REST shapes.
9. **Admin key** never logged; compare constant-time.
10. **Outgoing webhook secrets** optional; per-job `completion_webhook` is unsigned unless `completion_webhook_secret` is set (then same HMAC as org webhooks). On `PUT /api/v1/outgoing-webhooks/{id}` the org-webhook `secret` is **three-state**: omitted keeps the stored secret, explicit `null` clears it (deliveries go out unsigned), a string replaces it. Collapsing that back to "null means no change" reintroduces the un-removable-secret bug.
11. **Error bodies**: every 4xx/5xx is JSON with `code` + `message` (`middleware/error_body.rs` normalizes plain-text, empty and legacy `{error,...}` bodies; existing fields are kept). New handlers should still return `AppError`.
12. **Queue cap counts implicit queues** (configured ∪ holding jobs ∪ active schedule targets); jobs into an existing queue are never capped. See `dataflows/jobs-queue.md`.
13. **Worker registration is an upsert on `worker_id`** when the client supplies one; omitting it mints a UUID per registration. Both shapes must keep working — a stable id must not be double-charged against the plan worker cap, and an id owned by another org must stay a 409 (gRPC: `ALREADY_EXISTS`) with the neutral `WORKER_ID_UNAVAILABLE` text, the same words for a queue-scoped key naming a same-org worker outside its scope, so the answer never says whose id it is (BEJOB-19). REST (`workers.rs:149`) and gRPC (`worker_service.rs:354`) both register under `lock_resource(org,'workers')` in one transaction.
14. **One rule for "holds a worker slot"**: SQL `worker_counts_toward_cap(status, last_heartbeat)` (migration `20261011150300`: healthy, degraded, or draining with a heartbeat in the last 2 minutes). `get_org_resource_counts`, REST register and gRPC register must all use it; a second inline status list reintroduces the draining bypass. The claim path still does not require a registered worker (BEGRPC-15, deferred, owner decision).
15. **REST, `/auth/login` and gRPC authenticate API keys through `resolve_api_key`** (`api/middleware/auth.rs:480`). Every bcrypt on a request path goes through `bcrypt_gate::verify`; the failed-auth budgets (REST per client address, gRPC one shared bucket, `FailedAuthBudget`) gate only the legacy `lookup_hash IS NULL` scan, never a record-cache or `lookup_hash` match; a budget is charged BEFORE the scan (INCR, then compare) and refunded when the key is found or the scan never runs, so concurrency and cancellation cannot bypass it (W3R-08); REST/login and gRPC scan on separate turns (`bcrypt_gate::ScanLane`), so one transport's unknown tokens never delay the other's legacy keys; concurrent requests for one token share one scan (`LegacyFlight`); the wait for a turn covers a scan at the measured verify speed + 1 s, capped at 10 s, and a turn still busy is a 503 with `Retry-After` (gRPC `UNAVAILABLE`), never a 401 (W3R-07); a skipped or unrun scan is never negatively cached; legacy keys stay supported (operator decision); an auth DB failure is 503/500 with a generic message, never the sqlx text. See `dataflows/auth.md`.
16. **A claim must fit one gRPC message.** The server encodes at most `MAX_GRPC_MESSAGE_SIZE` (4 MiB) and tonic only enforces it after the handler returns, so every gRPC claim path (Dequeue, StreamJobs, ProcessJobs) measures the job before handing it out: batch cap 3 MiB, an unsendable job goes back to pending without a retry, a job over 4 MiB is dead-lettered (`queue_service.rs:735`, `:1823`). A new claim path must do the same.
17. **Settling a finished job is a conflict, not a miss**: REST 409 `CONFLICT`, gRPC `FAILED_PRECONDITION "Job is already <status>"` (ProcessJobs: `CONFLICT`); `NOT_FOUND` stays for another worker's or an out-of-scope job. A requeued job is "Lease expired". SDKs key on these.
18. **Inside a transaction (or advisory lock), never take a second pool connection.** Use the `_conn` variants (`limits::check_new_queue_limit_conn`, `check_resource_limit_conn`, `lock_resource`); pool-size concurrent callers otherwise deadlock the pool (BEOPS-10, `POST /workflows`). The StreamJobs claim transaction is the same: its rate-limit charge is Redis only, with the org's plan limits read from the locked key row (`LockedStreamKey`), never looked up on the pool (W3R-01).
19. **Migrations**: never edit an applied migration (sqlx checksums); the migrator ignores applied migrations this binary does not know (`db/mod.rs` `run_migrator`, `set_ignore_missing`) so an older image can boot after a rollback, but known checksums are still validated. New migrations start with `SET LOCAL lock_timeout = '5s'` and add foreign keys `NOT VALID`, then `VALIDATE CONSTRAINT` in a later step (W1-10). A `CREATE INDEX CONCURRENTLY` migration is a `-- no-transaction` file with exactly ONE statement and no `SET lock_timeout` (sqlx sends the file as one simple query, which Postgres wraps in an implicit transaction block that refuses CIC), paired with a transactional repair migration that drops and rebuilds the index when it is left `INVALID` (`20261013100000`/`100001`, `140000`/`140001`, `140100`/`140101`). They run over `DATABASE_DIRECT_URL` when set.
20. **Blank env equals unset** for every numeric, flag and optional-string setting (`config::env_parse`, `env_flag`, `non_empty_env`, `parse_cors_origins`), because `docker-compose.prod.yml` forwards `${NAME:-}`. Every setting the app reads must be forwarded by that file; `config::tests::prod_compose_forwards_every_operator_setting` guards the list.
21. **`/health` is 503 only when the database is down.** Redis, gRPC or the scheduler being down gives 200 with `status: degraded` and the flag false (`api/handlers/health.rs:93`). The process itself exits non-zero if the gRPC server, scheduler or metrics server dies (`main.rs:331` `supervise`), so a degraded `grpc`/`scheduler` flag is only seen for a stalled scheduler loop.
22. **Production refuses `EMAIL_PROVIDER=console`** (`Settings::validate`): login codes would only be logged.
23. **StreamJobs keeps one job with the worker per stream.** The next claim waits until the delivered job is no longer `processing` under its lease (`delivery_still_held`). An empty channel slot is not demand: the HTTP/2 transport pulls messages while the client's window has room (W3R-02). Test stream demand through a real tonic server and client, not the service in-process.
24. **A required Redis that is down at startup is kept as a reconnecting client** (`RedisCache::connect_at_startup`, required = `REDIS_URL` set or `RATE_LIMIT_FAIL_CLOSED`), never dropped to `None` for the process lifetime (W3R-04).
25. **System keys are not customer keys.** `api_keys.is_system` (migration `20261012110000`) marks the email-login key; `get_org_resource_counts` excludes it from `max_api_keys`, `get_or_create_email_api_key` (`email_login.rs:1585`) finds it by the flag (never by name), re-activating it skips the cap, and no API request can write the flag (create/update ignore it; `is_system` is read-only in OpenAPI). A new Spooled-created key must be inserted with `is_system = TRUE` or it eats a customer slot (BEAUTH-08, BEBILL-09).
26. **`max_workflows` counts only `pending`/`running` workflows**, in `get_org_resource_counts` (newest definition: `20261012110000`, which also holds the draining-worker and system-key rules; the next redefinition must start from it or it silently drops them). Anything that turns a workflow back into `running` (create, `POST /workflows/{id}/retry` `workflows.rs:631`) takes `lock_resource(org, 'workflows')` and pays `check_resource_limit_conn(+1)` first (BEBILL-10, BEFLOW-17, W4-01).
27. **Re-activating a row pays the cap, atomically.** `PUT /api-keys/{id}`, `PUT /schedules/{id}` and `PUT /outgoing-webhooks/{id}` with the row turning on: in one transaction `lock_resource`, re-read the row `FOR UPDATE`, and `check_resource_limit_conn(+1)` only if it really was off (two concurrent re-activations are charged once); turning a row off never checks quota; system keys skip the check. `PUT /schedules/{id}` recomputes `next_run_at` from now, as `/resume` does (BEAUTH-09, BEBILL-06, BEFLOW-07).
28. **`custom_limits` has one schema.** `OVERRIDE_KEYS` in `config/plans.rs` lists the keys: the eight resource caps (`max_jobs_per_day`, `max_active_jobs`, `max_queues`, `max_workers`, `max_api_keys`, `max_schedules`, `max_workflows`, `max_webhooks`: a whole number, or `null` / `-1` for unlimited, the same spellings as the `SPOOLED_PLAN_*` env vars) and five settings (`max_payload_size_bytes`, `rate_limit_requests_per_second`, `rate_limit_burst`, `job_retention_days`, `history_retention_days`: a whole number, `null` = plan default; retention 0..=`MAX_RETENTION_DAYS` 36500). Admin `PATCH` runs `validate_custom_limits` (400 `VALIDATION_ERROR`, every problem listed); runtime reading ignores a bad value (plan default). **SQL must read retention overrides only through `custom_retention_days(jsonb, key)`** (migration `20261012110100`), never `custom_limits->>'...'` cast to INT: one bad row used to make the retention statements fail for every org, and a stored `-1` deleted all of an org's completed jobs (BEBILL-07, BEBILL-26).
29. **Soft delete stops everything that acts without a key**, in one transaction (`admin.rs:536` `delete_organization`): keys revoked, `schedules.is_active = false`, `outgoing_webhooks.enabled = false`, `settings.webhook_token` removed, `plan_tier = 'deleted'`. The cron due-query (`scheduler/mod.rs:353` `process_cron_schedules`) and `POST /webhooks/{org}/custom` skip `plan_tier = 'deleted'`, like auth and realtime. Restoring `plan_tier` re-enables none of it. Organizations soft-deleted before 0.1.120 keep active schedules/webhooks in the database (outgoing webhooks are not filtered by `plan_tier`): `docs/guides/deployment.md`, "0.1.120 checks" (BEFLOW-06, BEAUTH-15).
30. **Client addresses for abuse controls come from `client_ip_from_peer`** (`api/middleware/client_ip.rs:117`) with the TCP peer (`PeerAddr` / `peer_addr`), never from `CF-Connecting-IP`, `X-Real-IP` or `X-Forwarded-For` read directly: those edge headers count only from an internal peer unless `TRUSTED_CLIENT_IP_HEADER` names the header, and ids go through `rate_limit_id` (IPv6 = its /64). `main.rs` must keep serving with `into_make_service_with_connect_info`. Email login: `start` is 3/min + 10/hour per client and may require a Turnstile token (`TURNSTILE_SECRET_KEY`, fail-closed 400 `CAPTCHA_FAILED`); `verify` is 5 guesses per (address, client) + 20 per address per 10 minutes, a throttled verify is 429 with `Retry-After`, and throttling never invalidates a code; a code is single-use via `AND used_at IS NULL` (BEAUTH-06, -10, -11, -24, BEBILL-24). See `dataflows/auth.md`.
31. **Rate-limit fields: two are not what the name suggests.** An API key's `rate_limit` is requests per MINUTE, checked after the org's plan token bucket, so it can only lower the plan limit (BEBILL-12). A queue's `queue_config.rate_limit` is accepted, validated, stored and returned but **not enforced by any claim path** (BEBILL-11, BEJOB-12, operator decision; enforcement is F02); docs must say "stored, not enforced yet", and nothing may imply workers are throttled by it.
32. **Row filters by an API key's queues call `queue_in_key_scope(queue_name, scope)`, never `queue_name = ANY(scope)`**, and Rust checks call `models::queue_scope_allows` / `queue_scope_is_unrestricted` (`models/api_key.rs:109`), the one rule REST, gRPC and realtime share. A `queues` entry is `*`, an exact name or `prefix.*`; a new query that compares with `= ANY`, or an inline copy of `q == "*" || q == name`, hides every queue a `prefix.*` entry covers and lets a key enqueue and claim but not settle or list (FEAT B2 / QW6, KEYS-1/2). Bind `ctx.queue_scope_filter()` (NULL = unrestricted). Keep `queue_scope_like_patterns()` `IMMUTABLE`, or exact-name scopes stop folding to an index condition. See `dataflows/auth.md`.
33. **The claim predicate must match `idx_jobs_claim`**: `organization_id = ? AND queue_name = ? AND status IN ('pending', 'scheduled') ORDER BY priority DESC, created_at ASC` in `CLAIM_BATCH_SQL` (`queue/mod.rs:62`) and in every gRPC claim query. The planner uses a partial index only when the query implies its predicate and can read it in the query's order, so widening the status list (adding `processing` or `failed`), dropping the `organization_id` / `queue_name` equalities, or changing the sort puts a 250 ms scan-and-sort per claim back at 300k pending jobs (BEJOB-03); extra filters (`scheduled_at`, `expires_at`, `dependencies_met`) are fine. Change the index (new migration) and the queries together; `w5_claim_query_uses_the_claim_index` checks the plan of the constant.
34. **Dependency-cancel reasons are shared constants**: `DEPENDENCY_FAILED_CANCEL_REASON` and `PARENT_FAILED_CANCEL_REASON` (`models/job.rs:133-142`, `DEPENDENCY_CANCEL_REASONS`) are what the scheduler's dependency sweep writes to `last_error` and what job and DLQ retry match to re-open a cancelled dependent. Change the text only there; a retry re-opens exactly those rows and never a job someone cancelled (BEFLOW-04).
35. **Retention never deletes a job whose workflow still exists, a job something still waits on, or a row a transaction holds.** Failed, dead-lettered and cancelled steps of an existing workflow stay until the workflow row is purged (workflow retention runs first in the pass); failed and dead-lettered jobs also stay while a pending, scheduled or processing dependent or child exists; every retention DELETE of rows that other requests change picks them `FOR UPDATE ... SKIP LOCKED` in the subselect, so status and age are re-checked on the newest row version. Every foreign key column that references `jobs(id)` needs an index (`schedule_runs.job_id`), or each batch scans that table once per deleted job (W5-R4, W5-R5, W5-R6). Open: the `expires_at` sweep still deletes workflow steps (BEFLOW-05). See `dataflows/jobs-queue.md`.
36. **A realtime stream ends with the credential it was opened with**: access-token expiry (+ leeway), logout / session revocation, key or organization state, and a maximum age (SSE 30 min, WS 1 h), re-checked at most every 2 s; per-organization stream caps are Redis sorted sets scored by heartbeat, never counters that a SIGKILL can leak (BEFLOW-13, BEAUTH-14, BEAUTH-19). A new stream type goes through `StreamAuth` and `ConnectionSlot`. See `dataflows/auth.md`.
37. **Outgoing webhook delivery is bounded and never spawns per event**: `spawn_dispatch` and `spawn_completion_webhook` queue or drop-and-count (`spooled_outgoing_webhook_deliveries_dropped_total`, `spooled_completion_webhooks_dropped_total`), one webhook may use at most a quarter of the slots and of the queue, and per-job completion webhooks keep their own slot pool and per-organization lane so a tenant's backlog cannot stall others. `spawn_completion_webhook` takes the organization id first (BEFLOW-10, BEFLOW-27, W5-R2). See `dataflows/webhooks.md`.
