# Backend invariants / compatibility

1. **Tenant isolation** is application `organization_id` scoping + API-key/JWT queue ACL. RLS is not a live backstop.
2. **Idempotent enqueue** when `idempotency_key` set: unique per org.
3. **At-least-once** processing: leases + retry + DLQ; workers must be idempotent.
4. **gRPC proto3 zeros** for `max_retries` / `timeout_seconds` mean “server default 3/300”, not zero. Documented in enqueue code comments. The same holds for `lease_duration_secs` / `extension_secs` on `Dequeue`, `StreamJobs`, `ProcessJobs` and `RenewLease`: `<= 0` is `GRPC_DEFAULT_LEASE_DURATION_SECS` (default 300; `0`/blank/unset = 300, above 3600 lowered to 3600, at or below `WORKER_HEARTBEAT_INTERVAL_SECS` or below 5 refused by `Settings::validate`; `config::WorkerSettings::grpc_default_lease_duration_secs`, `grpc/services/queue_service.rs:273` `lease_secs`, `grpc/mod.rs:91`), and `Register` reports that value. It is deliberately **not** the REST `WORKER_LEASE_DURATION_SECS` (30): the Go SDK `StreamJobs` has no lease parameter and the Go/PHP `Dequeue`/`RenewLease` send 0 unless set, so tying omitted gRPC leases to the REST default re-delivers their longer jobs to a second worker (W3R-03, backward compatibility wins). Explicit leases keep the 5..3600 clamp. Never hard-code a gRPC lease constant; change the setting. The default lease must stay above the heartbeat interval: `0` used to become a 5 s lease (and 1-9 a 5-9 s one) under the 10 s heartbeat, re-delivering every job of a worker that sends none.
5. **REST may send `max_retries: 0`** (instant DLQ on first fail). Clients must not assume REST and gRPC omit-semantics are identical for zero.
6. **Stripe webhook** must verify signature; events must be deduped; prefer 5xx over silent drop for ordering/link races.
7. **Plan limits** gate enqueue/resources; changing `config/plans.rs` or env plan overrides is a money-path change — owner sign-off.
8. **OpenAPI** is hand-maintained — update `docs/openapi.yaml` when changing public REST shapes.
9. **Admin key** never logged; compare constant-time.
10. **Outgoing webhook secrets** optional; per-job `completion_webhook` is unsigned unless `completion_webhook_secret` is set (then same HMAC as org webhooks). On `PUT /api/v1/outgoing-webhooks/{id}` the org-webhook `secret` is **three-state**: omitted keeps the stored secret, explicit `null` clears it (deliveries go out unsigned), a string replaces it. Collapsing that back to "null means no change" reintroduces the un-removable-secret bug.
11. **Error bodies**: every 4xx/5xx is JSON with `code` + `message` (`middleware/error_body.rs` normalizes plain-text, empty and legacy `{error,...}` bodies; existing fields are kept). New handlers should still return `AppError`.
12. **Queue cap counts implicit queues** (configured ∪ holding jobs ∪ active schedule targets); jobs into an existing queue are never capped. See `dataflows/jobs-queue.md`.
13. **Worker registration is an upsert on `worker_id`** when the client supplies one; omitting it mints a UUID per registration. Both shapes must keep working — a stable id must not be double-charged against the plan worker cap, and an id owned by another org must stay a 409 (gRPC: `ALREADY_EXISTS`). REST (`workers.rs:149`) and gRPC (`worker_service.rs:354`) both register under `lock_resource(org,'workers')` in one transaction.
14. **One rule for "holds a worker slot"**: SQL `worker_counts_toward_cap(status, last_heartbeat)` (migration `20261011150300`: healthy, degraded, or draining with a heartbeat in the last 2 minutes). `get_org_resource_counts`, REST register and gRPC register must all use it; a second inline status list reintroduces the draining bypass. The claim path still does not require a registered worker (BEGRPC-15, deferred, owner decision).
15. **REST, `/auth/login` and gRPC authenticate API keys through `resolve_api_key`** (`api/middleware/auth.rs:476`). Every bcrypt on a request path goes through `bcrypt_gate::verify`; the failed-auth budgets (REST per client address, gRPC one shared bucket, `FailedAuthBudget`) gate only the legacy `lookup_hash IS NULL` scan, never a record-cache or `lookup_hash` match; a budget is charged BEFORE the scan (INCR, then compare) and refunded when the key is found or the scan never runs, so concurrency and cancellation cannot bypass it (W3R-08); REST/login and gRPC scan on separate turns (`bcrypt_gate::ScanLane`), so one transport's unknown tokens never delay the other's legacy keys; concurrent requests for one token share one scan (`LegacyFlight`); the wait for a turn covers a scan at the measured verify speed + 1 s, capped at 10 s, and a turn still busy is a 503 with `Retry-After` (gRPC `UNAVAILABLE`), never a 401 (W3R-07); a skipped or unrun scan is never negatively cached; legacy keys stay supported (operator decision); an auth DB failure is 503/500 with a generic message, never the sqlx text. See `dataflows/auth.md`.
16. **A claim must fit one gRPC message.** The server encodes at most `MAX_GRPC_MESSAGE_SIZE` (4 MiB) and tonic only enforces it after the handler returns, so every gRPC claim path (Dequeue, StreamJobs, ProcessJobs) measures the job before handing it out: batch cap 3 MiB, an unsendable job goes back to pending without a retry, a job over 4 MiB is dead-lettered (`queue_service.rs:735`, `:1823`). A new claim path must do the same.
17. **Settling a finished job is a conflict, not a miss**: REST 409 `CONFLICT`, gRPC `FAILED_PRECONDITION "Job is already <status>"` (ProcessJobs: `CONFLICT`); `NOT_FOUND` stays for another worker's or an out-of-scope job. A requeued job is "Lease expired". SDKs key on these.
18. **Inside a transaction (or advisory lock), never take a second pool connection.** Use the `_conn` variants (`limits::check_new_queue_limit_conn`, `check_resource_limit_conn`, `lock_resource`); pool-size concurrent callers otherwise deadlock the pool (BEOPS-10, `POST /workflows`). The StreamJobs claim transaction is the same: its rate-limit charge is Redis only, with the org's plan limits read from the locked key row (`LockedStreamKey`), never looked up on the pool (W3R-01).
19. **Migrations**: never edit an applied migration (sqlx checksums); the migrator ignores applied migrations this binary does not know (`db/mod.rs` `run_migrator`, `set_ignore_missing`) so an older image can boot after a rollback, but known checksums are still validated. New migrations start with `SET LOCAL lock_timeout = '5s'` and add foreign keys `NOT VALID`, then `VALIDATE CONSTRAINT` in a later step (W1-10). They run over `DATABASE_DIRECT_URL` when set.
20. **Blank env equals unset** for every numeric, flag and optional-string setting (`config::env_parse`, `env_flag`, `non_empty_env`, `parse_cors_origins`), because `docker-compose.prod.yml` forwards `${NAME:-}`. Every setting the app reads must be forwarded by that file; `config::tests::prod_compose_forwards_every_operator_setting` guards the list.
21. **`/health` is 503 only when the database is down.** Redis, gRPC or the scheduler being down gives 200 with `status: degraded` and the flag false (`api/handlers/health.rs:93`). The process itself exits non-zero if the gRPC server, scheduler or metrics server dies (`main.rs:331` `supervise`), so a degraded `grpc`/`scheduler` flag is only seen for a stalled scheduler loop.
22. **Production refuses `EMAIL_PROVIDER=console`** (`Settings::validate`): login codes would only be logged.
23. **StreamJobs keeps one job with the worker per stream.** The next claim waits until the delivered job is no longer `processing` under its lease (`delivery_still_held`). An empty channel slot is not demand: the HTTP/2 transport pulls messages while the client's window has room (W3R-02). Test stream demand through a real tonic server and client, not the service in-process.
24. **A required Redis that is down at startup is kept as a reconnecting client** (`RedisCache::connect_at_startup`, required = `REDIS_URL` set or `RATE_LIMIT_FAIL_CLOSED`), never dropped to `None` for the process lifetime (W3R-04).
